<Story id="async-actions" label="Async actions">

<ComponentPreview name="alert-dialog/action" height={260} />

A confirm button that runs its own action and plays the whole lifecycle on the button.

Because `AlertDialogAction` is a Button that becomes an [Async Button](/docs/components/button#async-actions) when you pass `onAction` or `status`, it takes `onAction`, and the action's whole lifecycle plays on the button itself. The label morphs to a spinner and `pendingLabel`, then to a drawn check and `successLabel`, or shakes to a cross and `errorLabel`. Close the dialog once success has shown. After an error, keep it open so the person can try again. Flip the switch in the preview to see the failure path.


```tsx
<AlertDialog
  open={open}
  // The dialog can't be dismissed while the work runs.
  onOpenChange={(next) => state !== 'pending' && setOpen(next)}
>
  …
  <AlertDialogAction
    onAction={rollBack}
    pendingLabel="Rolling back…"
    successLabel="Rolled back"
    errorLabel="Rollback failed"
    onActionStateChange={(next) => {
      if (next === 'idle' && state === 'success') setOpen(false)
      setState(next)
    }}
  >
    Roll back to 3f9c2a1
  </AlertDialogAction>
</AlertDialog>
```

Reach for `ConfirmDialog` first. It holds the dialog through the work and shows failures as text, which suits most confirmations. `onAction` suits a dialog where the result belongs on the button.

## Installation & usage

<InstallTabs name="alert-dialog" noImport />

Use Alert Dialog before deleting a project, revoking a key or discarding unsaved work. Unlike [Dialog](/docs/components/dialog), it stays open when you press outside. Reserve confirmation for actions that are hard to reverse. For reversible actions, offer Undo in a [Toast](/docs/components/toast).

`ConfirmDialog` is the whole pattern in one component. Its confirm button says what it does, it stays open while async work runs, and it can ask for a typed phrase before a wide destructive action.

```tsx
import { useState } from 'react'
import { Button, ConfirmDialog } from '@youj/react'
import { TrashIcon } from '@youj/icons'

export function DeleteProject({ project }: { project: Project }) {
  const [open, setOpen] = useState(false)
  return (
    <>
      <Button variant="danger" onClick={() => setOpen(true)}>
        Delete…
      </Button>
      <ConfirmDialog
        open={open}
        onOpenChange={setOpen}
        destructive
        icon={<TrashIcon />}
        title={`Delete ${project.name}?`}
        description="Its deployments and domains go with it. This can’t be undone."
        confirmLabel="Delete project"
        challenge={project.name}
        onConfirm={() => deleteProject(project.id)}
      />
    </>
  )
}
```

`destructive` here is a boolean on `ConfirmDialog`; the trigger [Button](/docs/components/button) takes `variant="danger"`.

To lay one out by hand, compose the parts:

```tsx
import { useState } from 'react'
import {
  AlertDialog,
  AlertDialogAction,
  AlertDialogCancel,
  AlertDialogContent,
  AlertDialogDescription,
  AlertDialogFooter,
  AlertDialogHeader,
  AlertDialogTitle,
  AlertDialogTrigger,
  Button,
} from '@youj/react'

const [open, setOpen] = useState(false)

<AlertDialog open={open} onOpenChange={setOpen}>
  <AlertDialogTrigger render={<Button variant="outline" />}>Close editor</AlertDialogTrigger>
  <AlertDialogContent>
    <AlertDialogHeader>
      <AlertDialogTitle>Discard changes?</AlertDialogTitle>
      <AlertDialogDescription>Your edits haven’t been saved.</AlertDialogDescription>
    </AlertDialogHeader>
    <AlertDialogFooter>
      <AlertDialogCancel>Keep editing</AlertDialogCancel>
      <AlertDialogAction
        variant="danger"
        // The action doesn't close the dialog by itself.
        onClick={() => {
          discard()
          setOpen(false)
        }}
      >
        Discard
      </AlertDialogAction>
    </AlertDialogFooter>
  </AlertDialogContent>
</AlertDialog>
```

### Confirm and challenge

Name the action on the button: "Delete project" or "Delete 12 projects", never "OK" or "Yes". The label is the last thing people read before they commit.

`challenge` arms the confirm only once the exact phrase is typed, shown in a copyable chip above the field, and a check draws itself in the field when it matches. Reserve it for actions that are destructive and wide, like a bulk delete or anything with a name. On a small, common action it's friction that people learn to rush.

`onConfirm` decides how the dialog closes:

- A plain function runs and the dialog closes.
- A function that returns a promise keeps the dialog open while it runs. The confirm button shows a spinner and announces `pendingLabel`, Cancel and Escape are held, and the dialog closes when the promise resolves.
- `loading` forces the busy state, for work that something else drives.

### Touch

On a touch device an alert dialog stays a centered alert, the way a phone's own alerts are. Unlike [Dialog](/docs/components/dialog), it doesn't become a sheet and can't be pulled away: it's asking a question, and a swipe isn't an answer. Its actions stack at full width with the primary one on top, each at least 44px tall, and show the same press feedback as every button. The small size keeps its two buttons side by side. Nothing in it depends on hover.

Opened by a tap, focus goes to the alert itself rather than to Cancel or a challenge field, so the on-screen keyboard comes up only when someone taps the field.

</ReferenceRow>

#### Reduced motion

The dialog appears and leaves at once. Everything that reports progress still does, without moving: the challenge's check appears already drawn, a pending confirm shows a still spinner, and `onAction` swaps its label for text, with no morph and no shake.

<ReferenceRow title="Accessibility" summary="Keyboard, ARIA, focus">

### Accessibility

- The popup has `role="alertdialog"`. `AlertDialogTitle` names it and `AlertDialogDescription` describes it, so screen readers read the question and its consequence together.
- In `ConfirmDialog`, focus starts on the least destructive control: Cancel, or the challenge field when there is one. When you compose the parts, focus starts on the first focusable control in the popup, so keep `AlertDialogCancel` before the action, as in the snippets. Enter from the field confirms once the phrase matches. Opened by a tap, focus starts on the alert itself.
- A press outside neither closes the dialog nor moves focus. Escape cancels, unless async work is running. Focus returns to the element that opened it.
- While a confirm runs, the button keeps focus and sets `aria-busy`, and `pendingLabel` is announced. A failure is announced assertively through `role="alert"`. A matching phrase is announced as "Phrase matches".
- The media badge is decorative (`aria-hidden`), so put the meaning in the title.

</ReferenceRow>
