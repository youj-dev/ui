A change-password card: the new password gets a strength meter and a requirements checklist, and the confirmation checks that the two match.

`PasswordRequirements` ticks each rule as the password meets it, with a drawn check. The defaults are `defaultPasswordRequirements`: at least eight characters, upper and lower case, a number and a symbol. Pass `requirements` as `{ label, test }` pairs for your own, and reuse the same list to decide when the form can submit, as the demo does.

<Story id="reveal" label="Reveal">

<ComponentPreview name="password-input/states" height={260} />

The visibility toggle.

The eye button shows the password as text and hides it again. Pressing it with a pointer keeps focus and the caret in the field, so people can check a character mid-word and carry on typing. `visible`, `defaultVisible` and `onVisibleChange` control it from outside. While Caps Lock is on, a quiet mark sits beside the eye and screen readers hear it once.

</Story>

<Story id="strength" label="Strength">

<ComponentPreview name="password-input/strength" height={340} />

The strength meter as a password gets stronger.

`PasswordStrength` is a meter in four segments that fill from the inline start and tint from danger to success. The built-in estimate weighs length and character variety against common passwords, runs (`abc`, `321`) and repeats (`aaa`), and keeps anything under eight characters weak however varied it is. It's also exported on its own as `scorePassword`.

</Story>

<Story id="your-own-scorer" label="Your own scorer">

<ComponentPreview name="password-input/custom-scorer" height={240} />

A strength meter using a scorer of your own.

Pass `scorer` for your own policy or a thorough estimator such as zxcvbn or a server check. It returns a 0 to 4 score, or `{ score, label }` to name the step. `labels` renames all five steps, very weak to strong.

</Story>

## Installation & usage

<InstallTabs name="password-input" noImport />

Use it for every password: signing in, choosing a new one, confirming a change. `PasswordInput` alone is enough for a sign-in form. When people choose a password, add `PasswordStrength` and `PasswordRequirements` under it in the same [Field](/docs/components/field), so the rules and the estimate update as they type. For a one-time code sent by email or an authenticator app, use [Input OTP](/docs/components/input-otp) instead.

```tsx
import { useId, useState } from 'react'
import { Field, FieldLabel, PasswordInput, PasswordRequirements, PasswordStrength } from '@youj/react'

export function NewPassword() {
  const [value, setValue] = useState('')
  const rulesId = useId()
  return (
    <Field>
      <FieldLabel>New password</FieldLabel>
      <PasswordInput autoComplete="new-password" value={value} onValueChange={setValue} aria-describedby={rulesId} />
      <PasswordStrength value={value} />
      <PasswordRequirements id={rulesId} value={value} />
    </Field>
  )
}
```

`autoComplete` defaults to `current-password`. Set `new-password` when people choose one, so password managers offer to generate it. Point the input's `aria-describedby` at the checklist's `id` so the rules are read with the field.

<ReferenceRow title="Accessibility" summary="Keyboard, ARIA, focus">

### Accessibility

- The reveal button is named "Show password" and reports its state with `aria-pressed`. It keeps focus in the field on a pointer press, and it's a normal button for the keyboard.
- Caps Lock is announced once through a polite live region when it turns on.
- `PasswordStrength` is a `meter` labeled "Password strength" with the step's name as its `aria-valuetext`. Because a meter's value isn't announced as it changes, the new step is announced politely, once per change.
- Each requirement reads as "Done:" or "Not yet:" before its label, so the checklist makes sense without its icons.
- `autoCapitalize`, `autoCorrect` and `spellCheck` are off, so a revealed password isn't changed or underlined.

</ReferenceRow>
