# Architecture

How the docs site is built. See [README.md](../README.md) for setup and [CONTRIBUTING.md](../CONTRIBUTING.md) for adding pages.

## How it's built

- **Next.js 16** (App Router, Turbopack) with **fumadocs-core** and **fumadocs-mdx** for the content pipeline, page tree, search index and TOC tracking. Pages live in `content/docs/**/*.mdx`; sidebar order lives in each folder's `meta.json`. The site's chrome is its own, built from Youj: Fumadocs' layouts aren't used, only its MDX components and their CSS.
- **The controls** (`components/ui/controls.tsx`): the chrome's tabs, segmented controls and switch wrap Youj UI's own `Tabs`, `SegmentedControl` and `Switch`, so the site uses what it documents: at least 32px (40px on touch) in any preset, labels that truncate with a tooltip rather than squeeze, and glides on the `smooth` spring. A preview's toolbar is the exception, one compact row: its tabs, menus, segments and buttons all take the `control-xs` token (28px in the site's presets, 36px on touch; `compact` on `TabList` and `Segmented`, `TOOLBAR_MENU` and `TOOLBAR_BUTTON` in `preview-controls.tsx`), the tabs' labels a step down in mono capitals. The install and MCP tabs share it.
- **Code to take home** opens in one large modal, never a side panel: `CodeExportDialog` (`components/ui/code-export-dialog.tsx`, the kit's Dialog up to 1100 × 860px) split into sections, a nav of them on the inline start (the kit's vertical Tabs: an icon and a name each, the key gliding between them) and the open one beside it under its heading and a line on what it holds. It opens on the first section, the most useful. Where the dialog is narrower than 760px the nav is a row of tabs under the title, and on a phone the dialog is the whole screen (centered under a pointer, the touch sheet under a thumb); the head and the nav stay put while a section scrolls. Its parts are `ExportCommand`, `ExportCode` and `ExportSection`; a dialog can head its nav with a `preview` of what the code is for, and a section can hold a control at its heading's `end`. Create's Get the code, an icon's and a scene's code in the explorers (one shared instance each, loaded on first use; they open without a trigger, so `finalFocus` hands focus back to the control that opened them, or to its card after a pointer's close) and the illustration builder's export use it; a new export does too.
- **The shell** (`components/site/`): one header for every page, in the root layout. After the logo, four `NavigationMenu` menus (`lib/nav.ts`), sections, groups and categories only, never single pages (the sidebar and ⌘K hold those): **Docs** (Get started, Guides, Theming, Motion, Icons, Illustrations, Miniatures, Loaders in beta, Sound, AI & MCP and CLI and Figma, each a glyph, its name and a few words, opening its overview), **Components** (one column, the groups of `/docs/components`, heading its overview), **Blocks** (Cards, Sections, Screens and Frames, each opening its Blocks docs group's first page) and **Visuals** (the icon and illustration explorers, Miniatures and the loaders gallery). Each is a mega menu: its links in columns, then a feature card on its end side, one of the Youj loaders live on top (16:10, on the gallery's stage, in the site's own light or dark) over a title, a line and a link (Docs: Prompt, a command typed and checked off, to Installation; Components: Tabstop, a focus ring tabbing through a form, to All components; Blocks: Gantry, a part carried across a frame and set in place, to Create; Visuals: Draft, a draughtsman's lines drawing in, to the icon explorer). Every page carries the menus in its payload, so the header is given only them and the page index (`HeaderNav`), and a feature names its loader, never its code: `components/site/feature-art.tsx` loads each as a chunk of its own when its menu is pointed at, focused or opened, the panel mounts only while its menu is open, and a closing panel holds its frame; under reduced motion it's the loader's still frame. Tab and the arrow keys move between the menus and through a panel, Esc closes it back to its trigger. A particle above a trigger marks the current section (`activeSection`, from the menus' own URLs): Components on the components' pages, Blocks on the Blocks docs pages and Create, Visuals on the explorers and galleries outside the docs, Docs on every other docs page. On the right: ⌘K search (`CommandPalette` over the static index), then the community buttons (Discord and GitHub, from `site.links` in `lib/project.ts`, GitHub following `NEXT_PUBLIC_YOUJ_REPO_URL`; icon links with a CSS tip, so the header carries no tooltip code), then the sound toggle (`sound-toggle.tsx`), then the light/dark toggle, kept at every width; a first visit follows the OS's light or dark until the toggle stores a choice. A panel taller than the window scrolls inside itself. Below `lg` one bottom `Drawer` holds the same four menus as sections that open in place (the current one open, each led by its feature without a loop), the docs tree, and search with the community buttons and the sound toggle pinned to its bottom edge; opening it focuses the sheet, not the search row.
**The icons page** (`app/icons`, `components/icons/`): the showroom shell (`components/showroom`) with a library under it. The hero (`showroom.tsx`) puts one Youj icon on the paper stage with its panel (Style, and Motion or Transition) and a column of every Youj icon beside it (a strip and the search under the stage below lg); its state is `?icon=`. **Chain** is a mode of the hero: up to ten icons the stage morphs through, one `IconSwap` after another, listed in a card on the plate (below the plate on a phone) as the data table's column list is (`SortableList`, a line where the next pick goes); its state is `?chain=a~b~c`, and Copy code and Use it give code that steps through the list. The library under the hero (`explorer.tsx`) is every Youj icon in a virtualized grid: no toolbar or filter menu of its own: the hero's search is the way in, and the grid reads `q`, `type` and `category` (`category=arrows,status`) from the address. Each card is a small stage in CSS alone (`.icon-card-stage`), and pointing at it raises an island of actions (`card-actions.tsx`: Copy React code, Get the code, Download, or Open in Chain for a pair or state icon). A Youj card puts its icon on stage (or adds it to the chain while Chain is on, numbered on the card); Code opens the site's large code modal (`icon-code-dialog.tsx`). The explorer writes `q`, `type`, `source` and `category` and leaves the hero's parameters alone.
**The illustrations explorer** (`app/illustrations`, `components/illustrations/`, also at `/graphics`, the first link in the header's Illustrations menu): every isometric scene, read from the illustrations registry, so a scene added there appears here with nothing else to edit. On the showroom's shell, like the icons page: the hero first, with the viewfinder's island and the search beside it (by name, category, tag or what the scene shows, the icons' forgiving search, narrowed to any categories), and Gallery or Build as links to the two views (`views.tsx`); under it an "All illustrations" grid, one card per scene, which puts that scene on stage. The hero draws the chosen scene live in any preset and light or dark (scoped to its stage), its motion printed on the paper, with **Raw | In context** at the middle of the stage's top (raw by default: the scene alone and large; in context, the picture of a minimal screen it would live in, drawn large there too: an app's empty state, an onboarding dialog over the app, a site's hero, `context.tsx`), and Replay, Apart and Reduced motion on its toolbar; its panel (the showroom's panel grammar) says what it is (name, category and export, what it shows; its tags are the search's words, not the panel's; Docs and Builder by the area's name), then its Theme (the preset and the colors it takes, as the panel's rows) and **Use it** (Copy code, the scene by id, is an icon at the end of the stage's toolbar), which opens the large code modal (`scene-code-dialog.tsx` on the showroom's Use it grammar, `components/showroom/use-dialog.tsx`) with the scene floating at the head of its nav: Use it (Package or Copy in at its heading; 1 install, the package or `npx @youj/cli add illustration-<id>`, its own registry item, generated by `pnpm -F @youj/illustrations generate`; 2 the code, by id or as its own component), Download (the frame over its file cards: SVG, its colors resolved so it stands alone, or PNG at 1× or 2×, transparent or on the stage's canvas), Props, In a block (the blocks with an `illustration` slot) and Source, as the CLI writes it (`/r/illustration-<id>.json`, read when that section is first shown). The search, category and scene live in the query string.
**The loaders page** (`app/loaders`, `components/loaders/`, the Visuals menu's link and its docs at `/docs/loaders`): every loader in `@youj/loaders`, read from the loaders registry (`loader-<id>`, one item per loader with its category, tags and loop length, written by `pnpm -F @youj/loaders loaders:generate`), so a loader added there appears here with nothing else to edit. It's on the showroom's shell (`components/showroom`, as /miniatures and /illustrations are): one loader on show in the hero, live on the paper stage, drawn at the size set in the panel through its own `size` (a loader is drawn from code, so it's never a scaled-up picture) with its own label under it; the viewfinder's island on the stage's lower edge and the search beside it (by name, export, tag, category or what it shows, narrowed by category chips; `/` opens it); and every loader as a card under the hero, drawn once the page is idle. **Raw | In context** sits at the middle of the stage's top (raw by default): in context the loader sits in a screen where a large loader is what you'd wait on, chosen by its category (a deploy's status page, an upload's processing card, an assistant thinking, a dashboard's chart, an app's launch screen: `context.tsx`, a chunk fetched once the page is idle), as large as it is raw, gliding the few px into place without restarting. Its status (playing and its loop's length, held or still, and the label it says first) is printed on the paper, and Replay, Hold and the playback speed (1×, 2×, ½×: the stage's clock, never the code) follow on the toolbar. The panel (the showroom's panel grammar) holds its name, category and export and what it shows (its tags are the search's words, not the panel's), with Docs by the area's name; then its settings on the panel's even rows (`tune.tsx`): **Size & speed** (the stage draws the loader at the size set, 200 px to start, as large as its room allows past that; Speed, 0.5× to 2×); **Colors**, the **Primary** and **Secondary**, `color` and `accentColor`, which the stage and the thumbnails wear too; and **Label**, shown or not from its heading: its **Text** (the first label typed in place; every label, one a line, in an editor laid over the panel, so the rows never move; several take turns), **Position** as segments, **Effect** a menu, and over or under the drawing its type, **Font** (with capitals at its end) and **Font size**, as the kit's label properties (`--yj-label-case`, `--yj-label-font`, `--yj-label-size`); all written into the code. Copy code (the loader as tuned) is an icon at the end of the stage's toolbar, and the panel ends in **Use it**, the large code modal (`code-dialog.tsx` on the showroom's Use it grammar) with the loader live at the head of its nav: Use it (Package or Copy in at its heading; 1 install, the package or `youj add loader-<id>`; 2 the code with the look set here), Props, and Source as the CLI writes it from `/r/loader-<id>.json`. Only the stage plays: each loader is a chunk of its own (`generated/loaders.ts`, written by `scripts/loaders.ts`), the stage fetches the one on show and its neighbours, and every thumbnail is its loader's still frame (a paused canvas, never on the ticker), drawn only once it's near the view; the strip, the search and the cards are memoized, so the panel's controls re-render none of them. The loader on show is `?id=` (what ⌘K's results link to); `?strip=column|bar` stands the viewfinder elsewhere.
- **Docs pages** (`components/docs/`): the tree (`page-tree.tsx`) in a `ScrollArea`, the TOC with a thumb over the headings in view (a rail from `toc:`, 86rem, where the page's column fits beside it; below that, an "On this page" popover in the page's header), prev/next cards, and a page's arrival (`pending-page.tsx`, `.docs-page[data-arrive]` in `styles/site.css`): a navigation swaps the page at once, and its title, lede, first four blocks, rail and page band's scenes rise 6px into place one after another, in CSS alone; never on the page a visit lands on, a hash change or under reduced motion.
- **One column.** A docs page is one column, `--docs-column` (48rem), centred between the sidebar and the TOC, and every block fills it: the title and description, text, headings, callouts, steps, previews, code, tables, the Reference, the pager and the footer all share its two edges. 48rem holds a live preview and ~95 characters of code, and it's the room between the sidebar and the rail at 1440. The page's text is set a size up from the prose default (16px on a 1.75 leading) so the column stays the measure it always read at, 48 ems; code and tables scroll sideways inside it when they're wider. The docs frame grows to `--docs-width` (110rem), wider than the landing's `--site-width`, so on a big screen the sidebar and TOC keep to its edges and the column stays centred with even room either side. `full: true` in a page's frontmatter drops the TOC and widens the column to 70rem.
- **The homepage** (`components/landing/`): a live product built from the kit, the eight parts (UI, Motion, Loaders, Icons, Illustrations, Sound, Themes, and Blocks, which opens the Screens docs), the card that pulls apart into eight layers (Blocks are its floor, the page it sits in; Loaders a loader on its stage), the packages and a registry explorer, themes, quality, and three ways to start (the whole kit, one piece, a whole page). The family is eight tiles in full rows (one, two from `sm`, four over four from `xl`): Illustrations draws live scenes from the registry, one after another; Sound the header's waveforms, drawn and never played; Loaders mounts a loader, live, from a chunk of its own once the tile nears the screen (the server sends its empty stage; reduced motion shows its still frame); and Blocks an app frame whose blocks drop into place (`blocks-frame.tsx`, which the third way to start shows too, drawn only in the browser there). A live loader anywhere on the homepage is a lazy chunk: the hero's is fetched the first time the stack comes apart and plays only while the stack does. Every count comes from the registry fragments (`lib/catalog.ts`), so none can drift from what ships. The "In motion" section plays the homepage's own film (`<Film>`), named in `public/promo/manifest.json` under `home` (`readHomeFilm()`). It's a seamless, silent loop rendered in each scheme, and `<LoopVideo>` plays the cut that matches the page, with a pause button. A theme switch mid-play picks the other cut up where it was, over that scheme's poster. The poster is the film's first frame, and it's all that shows under reduced motion or Save-Data. Without the film, the section is left out. Each of the five parts has a topic loop in `public/promo/manifest.json` (`readLoops()`), played at the top of its docs overview (`<TopicLoop topic="…" />`, the 16:9 cut in a dark frame, with a pause button). `<Family>` plays a part's strip cut in its tile when it's given `loops` (`<LoopVideo>`, in the page's scheme, cropped from the middle); the homepage gives it none, so its tiles stay live sketches, and the videos and posters are on R2 (see Media on R2), `public/promo` holds only `manifest.json` and `og.png`, and the strip and 4:5 cuts are rendered on request into `apps/promo/exports`, which is gitignored (`components/landing/promo-files.test.ts` holds the folder to it). The poster is painted first; the loop loads once the page is idle and the box is near, plays only while a quarter of it is on screen in a visible tab, and never loads under reduced motion or Save-Data. A part without a published loop keeps its live sketch.
- **One Tailwind root, two sheets.** `app/tailwind.css` imports `@youj/core/styles/youj.css` (which owns the Tailwind import and the palette), then `@youj/react/styles/ui.css`, then the component styles' recipes (`@youj/react/styles/bezel.css`, which apply wherever `data-yj-look="bezel"` is written: a preview set to the Bezel style), then Fumadocs' component CSS. `styles/theme.css` points every Fumadocs variable at a youj token, `styles/prose.css` sets the long-form typography, and `styles/site.css` holds the site's own language: the construction frame, display type, and the landing's inspect and layer styles. Fumadocs' typography plugin is left out on purpose: a JS plugin puts Tailwind in compat mode, which drops the theme colors declared after youj's `--color-*: initial`. That root is compiled twice and never loaded itself. `app/global.css` (every page, from the root layout) adds `@source not` for the blocks' folder in `packages/ui/src`, so docs and marketing pages ship a sheet about a fifth smaller. `app/gallery.css` compiles the root with those folders scanned and `postcss/gallery-delta.mjs` (a PostCSS plugin listed after Tailwind in `postcss.config.mjs`) takes out every rule, selector and declaration `global.css` already has, so what is left is only what a page rendering blocks needs on top. Code that renders them imports it: `components/showcase/render-story.tsx` (the components list's live stages and the bare `/view` pages, which the docs' block previews load) and `components/create/create-view.tsx` (Create's frame is built from blocks). A route that imports neither never loads it; a new one that renders a block or an example through one of those two gets it. Tailwind orders a sheet by variant first and property second, so two rules that set one property must sit in one sheet to keep that order (split across two, the later sheet's `pt-20` beats an earlier `md:pt-28`). `scripts/gallery-core.ts` (part of `generate`) therefore writes `generated/gallery-core.txt`: every class a block or example writes beside a same-family class under another variant (`pt-20 md:pt-28`, `p-4 md:pt-8`), which `tailwind.css` reads as a source so those stay in `global.css`. Classes it can't see together (a block's `className` on a component whose own classes set the same property under another variant) are the split's residual risk: after changing the sources, compare a page's computed styles with one sheet and with two, and write a class that differs beside its neighbour in the block. `postcss/gallery-delta.test.ts` and `scripts/gallery-core.test.ts` hold the trimming and the pairing. Add a source folder to the split with an `@source not` in `global.css`.
- **Theme.** `next-themes` writes both `class="dark"` (Fumadocs) and `data-theme` (youj) on `<html>`. The site's frame wears **Basalt in dark and, in light, `SITE_LIGHT`** (`lib/site-light.ts`: Basalt's character, the Clean style's Inter, sentence-case labels, rounded controls, density and flat cards, with ink actions, in Graphite's colours, a site-only blend; the shipped presets are untouched), Classic always. Previews start in the stock preset for the mode (`SITE_PRESET` in `lib/site-mode.ts`: Graphite in light, Basalt in dark). The frame's variables are CSS, in a `<style>` the server puts in `<head>` (`siteThemeCss` in `lib/site-preset.ts`: Basalt on `:root`, `SITE_LIGHT` on `:root[data-theme='light']`), so next-themes' pre-paint script picks the side before first paint and hydration changes nothing; the root `YoujProvider` carries no theme, and `<html>`'s `data-yj-theme` is only a marker kept in step with the mode. Inter and JetBrains Mono come from @fontsource (the site's own faces and the Clean style's); Geist and Geist Mono are self-hosted for previews in the Bezel style, fetched only where one shows. It is dark by default; its only switch is light or dark, through `lib/site-theme.tsx`, which reveals the new mode as a circle from where it was asked for (View Transitions; instant under reduced motion). Presets, the component style and motion settings belong to the previews (`lib/preview.ts`): a component preview's toolbar, the theme bar on Blocks and Examples, and Create each change only what they render. Old stored choices (`youj-site-preset`, `-style`, `-motion`) are read by nothing.
- **White chrome, gray stages, white components.** The light presets lay an app out (white cards, menus and fields on a soft gray page), while the site's own light theme has a white page (`SITE_LIGHT`, `neutral.page: 'white'`), so the page and prose are white and code and command blocks (`bg-surface`) the soft gray. The site paints with the core roles only (no literals, no `/N` tints, no `dark:` colour forks). Library output stands on a `<Stage>` (`components/site/stage.tsx`), the only site element that writes `data-yj-theme`/`data-theme` below `<html>`: a theme scope in its own page colour, with a `.site-card` frame around it. Website-like blocks (marketing, content, auth) render on the white page a site has; app, frame, commerce and lifestyle blocks keep the gray (`lib/showcase.ts`'s `page`; a story overrides it with `showcase: { page: 'gray' | 'white' }`). The header, docs sidebar and islands are chrome tone scopes (`data-yj-tone="chrome"`, `bg-chrome`/`bg-chrome-float`), so a site theme with `tone.chrome: 'dark'` darkens them and their menus, search trigger and tips follow by derivation. The `light:` variant (`styles/site.css`) is for brand art only.
- **The dev panel** (local `next dev` only: Shift+Alt+D or `?dev=1`; never in staging or production builds; `components/site/dev-panel*.tsx`, `lib/dev-theme.ts`): a lazy chunk that loads nothing for visitors. A preset gallery (`DEV_PRESETS`: the site, every preset, Paper and two-tone looks) puts the whole site in a look on `<html>`; the controls (`FIELDS`, one per input, tone and info included) edit from it, Reset returns to it, and Copy values prints the whole `defineTheme`.
- **Logo, tab icon and browser bar** follow the mode. The logo is the word on its own in the text colour, no badge, and its one colour, the j's square tittle, is Basalt's yellow in dark and the light theme's Graphite blue in light; at the header's 24px the tittle is grown 1.3× so it reads. The footer's page-scale wordmark is the same lettering. The badge is for icons: `pnpm -F docs favicons` (`scripts/favicons.ts`) writes `public/icons/basalt-dark.svg` and `site-light.svg` and 32px PNGs from the mark (the u holding the tittle, in a badge in the ink, the u in the canvas) hand-hinted for 32px (`faviconSvg`) and the preset's colours (`lib/site-brand.ts`; on light's near-black badge the blue tittle is lifted to OKLCH L 0.66 so it reads), plus `app/apple-icon.png` (the mark full bleed, from `appIconSvg`) and `public/favicon.ico` (the 16px and 32px hinted designs) in the default, Basalt dark; `lib/site-brand.test.ts` fails while they're stale. A tiny script in the layout's `<head>` writes the stored mode's `<link rel=icon>`s and `<meta name=theme-color>` before first paint (dark when nothing's stored, the OS's for "system"; React doesn't render them, since it hydrates a link by its href), and `SitePresetMarker` in `app/providers.tsx` swaps them on every toggle.
- **Sound.** Off by default. The header's toggle (`components/site/sound-toggle.tsx`; in the mobile sheet's bottom bar below `md`) turns interface sound on: a toggle button named "Sound" with `aria-pressed`, the speaker's waves drawing in or crossing out, and a CSS tip that says "Sound on" or "Sound off". The choice is the visitor's, kept in localStorage (`lib/site-sound.ts`, key `youj-sound`, in step across tabs). The root `YoujProvider` (`app/providers.tsx`, above search so the palette's cues sound too) carries the sound: with sound off it has no `sound` and nothing sound-related loads; the first time it's on, `site-sound-on.tsx` is imported (`@youj/sound`'s Beacon pack, its player and the pack's audio, chunks of their own) and handed over as `sound`, and the toggle is `sound.muted`, so turning it on or off never remounts the page. Every Youj component on the site plays its cue (buttons, tabs, switches, dialogs, toasts, code blocks' copy), and the site's own controls emit theirs through `useSoundCue`: the header menus open and close when a press or a key opens them (never on hover, nor on following a link), the mobile sheet, the search palette's and the code modal's first open (their code arrives with it), the theme toggle, and the site's copy buttons (success, or error when the clipboard is blocked). The press that turns sound on is answered with `toggleOn` once the pack can play; turning it off plays `toggleOff`. Nothing plays before a gesture or on a page load, and it plays under reduced motion too, since the visitor asked for it. The promo films and topic loops stay silent.
- **Motion.** The root `YoujProvider` (`app/providers.tsx`) holds the site's clock: the motion personality both presets share (`precise`, read from `<html>`) at 1×, following the OS's reduced-motion setting. Every preview's toolbar has a Motion menu (`components/ui/preview-controls.tsx`: a speed, 2× to ¼×, or the reduced state) that reaches only its own stage or frame.
- **Server components** can't import the `@youj/react` barrel (not every module in it is marked client), so they use `components/ui/button-link.tsx` for button-styled links and `components/client.ts` for motion's hook-using exports.
- **Code highlighting** uses a theme made of CSS variables (`lib/code-theme.ts`), so one highlight pass serves both themes. Every highlight on the site goes through `codeHighlight` there: a token's colour is a class (`ck`, `cs`… in `TOKEN_CLASS`, set in `styles/theme.css`), default-coloured text is bare, and neighbours of one colour are one span. A new highlight call spreads `codeHighlight` rather than passing `themes`.
- **Static everywhere.** Every page, the search index (`/api/search`, searched in the browser) and the registry are prerendered.
- **Page weight.** What a page carries in its HTML and its RSC payload is held to a budget per kind of page (`scripts/page-weight.ts`; the limits, and the JS budgets of `scripts/js-budget.ts`, live in `scripts/budgets.json`, run by `build` after `next build`, or `pnpm -F docs weight [dir]` on a build or a static export): it prints the heaviest page of each kind and fails on any page over its budget. What keeps pages light:
  - **Code tabs fetch their code.** A docs preview's Code tab, and a block's or example's file list, carry only file names (and lengths). Each file is prerendered as JSON by `app/code/[...path]/route.ts` (`/code/docs/button/demo.json`, `/code/blocks/app-billing/<install path>.json`, from `lib/code-files.ts`): its text and its highlighted markup. A tab fetches the file it shows the first time it shows it, a pointer or focus on a tab starts the fetch early, each file is fetched once per visit (`lib/code-load.ts`), and the panel shows a placeholder while it loads and a retry if it can't (`components/ui/code-source.tsx`). The copy button waits for the text; the .zip fetches any file not yet shown.
  - **The docs tree only where it's drawn.** The docs layout gives its sidebar `navTree()` (`lib/tree.ts`): names, links, group pages and badges (`status`), without descriptions or Fumadocs' ids and refs. The header doesn't carry it: the mobile menu fetches `/docs-tree.json` (the same data) when it's about to open. The header's list of real pages (for the 404) is written by folder (`lib/page-index.ts`).
  - **The icon names only when searching.** The search palette matches icon names, but they aren't in every page's payload: it fetches `/icon-names.json` (`app/icon-names.json`) the first time it opens.
  - **Builders are drawn in the browser.** The Sound builder (`components/sound/sound-builder-lazy.tsx`) is a box of its height until it nears the screen, a link carries picks, or its button is pressed.
  - A new client component that takes a big prop (source, a tree, a table) ships it in every page that renders it, twice (the HTML and the payload): publish it as a static route and fetch it when it's needed, as the Code tabs do.
  - **One class for a repeated part.** A class string is written into the page once per element, in the HTML and again in the payload. So the docs' server-rendered parts that repeat on a page (heading anchors, cards, code frames, inline code, and each row of a props table or motion spec) wear one named utility each (`props-row`, `heading-anchor`…, `styles/site.css`), which `@apply`s the utilities it replaced. Before, class strings were about a quarter of a docs page's payload. A new part that repeats per row does the same.

## Preview size

Every preview's View options (a docs example's, a block's or example's frame) has a **Size** section (`components/ui/preview-size.tsx`): the layout density (Standard or Compact) and the UI scale (75% to 120%) the demo renders at, what an app sets on its root `YoujProvider`. Every preview starts at the standard size (`defaultSize` in `lib/preview.ts`): roomy at 100%, the provider's own. Compact at 90% is the option for dense pro tools. A pick re-renders the preview at once and is the reader's, per axis, shared by every preview and remembered in localStorage (`lib/preview-size.ts`, key `youj-preview-size`); Reset forgets it, and each preview returns to its own. A framed demo gets it over `lib/frame-sync` (`size` in the state). View options' trigger carries a dot once the preview is off its default. The components list has no Size control: size is a preview's. Create's size is its own (the link's `layout` and `scale`, `packages/ui/src/docs/create/size-url.ts`).

## Device preview

Every example frame shows both experiences of the library. The **Device preview** control (Pointer | Touch, in View options' Device section) is global and remembered like the component style (`lib/device-preview.ts`, key `youj-preview-device`). Until a reader picks, it follows the hardware (touch on a phone, pointer on a desktop) and writes nothing.

- **Touch on a non-touch screen:** the stage draws a phone (a 390px screen with a hairline bezel). The demo runs in `YoujProvider device="touch" portalContainer={screen}`, so sheets, menus, dialogs and tooltips portal into the screen and rise from its bottom edge. The screen is a `fixed` containing block (`transform`, `contain`; the CSS is in the `device preview` block of `styles/site.css`).
- **On touch hardware:** no phone; the stage is full width and Pointer forces `device="pointer"`.
- **Toolbar:** one row at every width, never wrapping, like every preview toolbar on the site: the tabs; then the look (the theme specimens and the styles, from `sm` up), **View options** (`components/showcase/view-options.tsx`: Size, Motion and Device; the kit's Popover, so a bottom sheet on touch, which on a phone also holds the look) and Replay. The shell (`preview-frame.tsx`) draws the same row with the same classes (`TOOLBAR_ROW`, `TOOLBAR_END`), so nothing moves when the live toolbar arrives; the popover comes with the live chunk, never the shell's.
- **Wide demos** scroll horizontally in the stage with an edge fade rather than being clipped.
- Limit: a demo's own `sm:`/`md:` styles still follow the browser window, not the 390px screen.

## The levels

Everything sits on one of five levels (`taxonomy.json`: components, simple or composite, are imported from packages; cards, sections, frames and screens are copied in; cards, sections and screens are the Blocks). Everything is documented in the docs, and there are no galleries: a component is its docs page; every block is documented in a story on a Blocks docs page, its only page: a `<BlockStories>` page per family in `content/docs/blocks/(cards|sections|screens)` (`lib/block-docs.ts` reads which story documents each block; `lib/block-docs.test.ts` and `test/parity.test.ts` fail on a block without one). The frame's parts have no page and no search result: they're chosen in Create, which installs them with its export. The old galleries (`/components` and its categories, `/cards`, `/sections`, `/screens`) and every item's own page (`/cards/<name>`, `/frames/<name>`…) redirect in one hop: a list to its docs group's first page (`/components` to the Components docs, `/frames` to Create), a category to the docs page named after it or that opens its group or documents most of it, a block to its story. The items list themselves from `@youj/react` (`lib/showcase.ts`, filed by `lib/levels.ts`), so nothing here changes when one is added:

- **Theme audit.** `node scripts/theme-audit.ts <base URL>` (against `next start`; it reads the blocks and examples from `lib/showcase.ts`) drives every item through every preset, light and dark, and reports any that keep a theme of their own: by the theme variables across the demo against the frame's preset. `lib/showcase.test.ts` guards the causes it has found, from the source: a `ThemeScope` over a theme the bar can't override, a theme seeded once from the one around it, a story that drops the `theme` arg.
- **Blocks** (cards, sections, frames and screens) are the `registry:block` items in `packages/ui/registry/ui.json`, each filed by `taxonomy.json` and grouped by folder on disk (Auth, App, Marketing, Commerce, then any new one). **Each is framed by its kind** (its story's `showcase.kind`, `framing` in `lib/showcase.ts`), everywhere it's shown (the docs story's frame and `/view`): a screen or an overlay in the 1280×800 frame (an overlay open over `PlaceholderPage`, a quiet sketch of an app page under a scrim); a section full-bleed and as tall as it is; a card, and a fragment, at its own width, centered on a plain stage with no screen drawn around it, as tall as it is. The frame's parts are the exception: their stories show them in the whole app frame. A section's or card's `/view` page renders on `components/showcase/kind-stage.tsx`, which holds any `min-h-dvh` page inside it to its content (`[data-kind-stage]` in `styles/site.css`) and reports the stage's height to its frame (a `size` message on `lib/frame-sync`; the frame keeps the tallest it has heard until the demo reloads or its width changes, so content sized by the viewport can't shrink it in a loop). A card's frame isn't zoomed. A block's story on its docs page (`components/docs/block-stories.tsx`) frames it, shows the files `youj add` writes, its usage and its Reference (props, strings, what it's built from); a frame's sidebar shows the AppFrame it draws as its usage, the frame's other parts their own. A block's Usage, Props (with its item types) and `copy` keys, read from the block's source by `scripts/props.ts` (`generated/block-props.json`, keyed by item name): the snippet (`lib/block-usage.ts`) passes its data props through a typed wrapper, shows one `copy` string and stubs each `on…` callback; a block that takes none of them says it's demo content to edit after adding. A frame part on a docs page (a sidebar) gets its data through the frame, so its usage is the `AppFrame` it sits in, routed by the app (`frameUsage`), and its Props add AppFrame's and the nav's shapes. The frame's parts (sidebars, top bars, accounts, search…) are frames, documented with the app shell (`FRAME_BLOCK`), which composes them, on the Frames pages; each installs on its own, and Create puts them together.
- **The demos** render through their stories at `/view/<blocks|examples>/<slug>?story=<Export>` (a component's, `/view/component/<slug>`), a bare page with no site chrome, loaded in an iframe so the demo's breakpoints answer to the frame's width. `scripts/showcase.ts` (run by `generate` and `typecheck`) writes the loaders to `generated/showcase.tsx`.
- **The frame** (`components/showcase/viewport-frame.tsx`) is a bezel with a screen of its own: canvas, border, radius and shadow, floating on a drafting desk when it's narrower than the stage. Preview snaps to desktop, tablet or phone (or drag the handle). Its toolbar keeps to the essentials: Preview | Code, the Story and Illustration menus, the page's look (`picker`, the theme bar, from `lg` up), **View options**, Reload and Open in a new tab (hidden on a phone); one row that never wraps. View options (`view-options.tsx`) is the kit's Popover (a bottom sheet on touch) with everything else in sections: Viewport (device width and zoom, with the width and scale the demo is drawn at), Size, and Motion (speed and reduced motion); below `lg` the look moves into it too. Its trigger carries a dot once anything is off its default. On block and example pages the frame zooms (`zoomable`): Fit, the default, lays a desktop demo out at 1280px and scales it to the frame (100% on a frame under 768px, where the demo's own small layout is the honest view), or 50%, 75% and 100%; ⌘/Ctrl − and + step through them from anywhere in the frame, the demo included, and the choice is remembered in localStorage. The Story menu is the kit's `Select`. A block with an illustration slot gets an Illustration menu (`illustration-picker.tsx`): its trigger shows the scene in miniature, and it opens a search over every scene, grouped by category as a grid of thumbnails, with arrows that move in two dimensions; the chosen id reaches the demo as `?illustration=<id>`. Code (`code-panel.tsx`) shows the install command, the files as `youj add` writes them (each fetched from `/code/…` when it is first shown; see Page weight), per-file copy and a `.zip` built in the browser (`lib/zip.ts`).
- **The theme bar** (`components/showcase/theme-picker.tsx`, `lib/showcase-theme.ts`): a preview's toolbar picks the look it wears, and nothing else on the site: a preset from the library's `themes` (the stock preset for the mode until one is picked: Graphite in light, Basalt in dark), each shown in miniature (its accent, corner radius and type) by `ThemeSelect`, and the component style (Clean, the default, or another) by `PreviewLook`. A docs preview's pick is its own and nothing goes in the URL (`?theme=` and `?look=` still read on `/view` pages); a stale value (the old `site` or `custom`, a preset the library dropped) reads as the default. Items that take `theme?: ThemeInput` get the chosen preset as that prop; anything else follows the frame document's preset.
- **Live theme** (`lib/frame-sync.ts`): a frame's page starts in the site's preset for the mode, and the page talks to it over `postMessage`. The frame says hello; the page answers with the site's light or dark, the theme bar's preset and style, and the frame's own speed and reduced motion (its toolbar's Motion menu), and again on every change. The frame applies them to its own document without a reload or a write to storage, and says when its demo has painted, so the page fades it in with no flash.
- **The component style is the previews'.** It never touches the site's own chrome, whose root provider says `look="classic"`: in-page previews get the style on their stage's `YoujProvider`, framed ones over `lib/frame-sync` (a state without a style is Clean), and Create's preview wears the style of its own link instead.
- **A picked look sweeps in.** A pick in the theme bar wipes each preview on screen to the new preset or style from the side the selection moved away from, on the site's `slow` token: a live frame in a view transition of its own document (`lib/frame-sync.ts`). The sweep's clip and edge come from `lib/showcase-theme.ts`. Light or dark is left to the page's own reveal; frames out of view, and reduced motion, swap in place.
- **Component previews** (`components/docs/preview-frame.tsx`, `preview-live.tsx`): a page ships each example as a shell and hydrates almost none of it on arrival. The shell is server-rendered: the Preview and Code tabs (plain buttons, so Code works at once), the stage as an empty box at its full height (so nothing moves when it fills: `height`, or what the demo measured when it's taller, per side of `sm`, from `lib/stage-heights.json`), marked `aria-busy` until the demo arrives, and an empty code panel, which fetches the example's source when the Code tab first opens (see Page weight). `preview-frame.tsx` wakes the frame when it comes within 200px of the viewport, or a mouse is over it, or a key or keyboard focus is inside it (not a press or a touch: the live toolbar replaces the shell's tabs, and a click whose target was swapped between down and up would be lost). Waking loads `preview-live.tsx` as a chunk of its own, with the toolbar's menus, the stage's providers, the examples index (`examples/index.tsx`, one `dynamic()` per demo) and the demo, and it takes the shell's toolbar and stage place; focus goes back to the tab it was on. A lazy Suspense boundary around the live frame was tried and doesn't work here: React client-renders a dehydrated boundary when a context above it changes (the theme provider's `mounted` flips right after hydration), and it outlines large ones, which reveal late. Each toolbar holds the look (`PreviewLook` in `components/showcase/theme-picker.tsx`: the presets as the galleries' specimens, the mode's default chosen until one is picked, and the Bezel / Classic switch), View options and Replay. The preset changes that preview alone: its `YoujProvider` carries the preset (the stage's canvas and type wear it too), the style and the clock.
- **Stage heights** (`scripts/stage-heights.ts`, `lib/stage-heights.json`): a page's `height` is a minimum, and a demo that outgrows it (it wraps on a phone, it has more rows) would push the page down as it mounts. The script loads every page with an example on a running site (`node scripts/stage-heights.ts [--url …] [--chromium …]`), on a phone and a desktop with reduced motion, wakes each frame and measures its demo, and writes each demo taller than its page's `height` as `[phone, from sm up]`. `ComponentPreview` reads it at build time, and the shell and the live stage keep that height (`stageBox`, `lib/preview.ts`). Run it again when a demo changes size; a stale entry only costs the difference.

`test/parity.test.ts` fails when a UI component, block, example or motion export has no place on the site, when a page is missing from its folder's `meta.json` or from its group's page, and when the badge policy slips. Its allowlists name the internals that don't get pages, each with its reason.

## Create

`/create` (`app/create`, `components/create/`) builds an app frame from the `frame` blocks (`packages/ui/src/blocks/frame`: a sidebar, a top bar, an account and a search, composed through the frame shell), fills it with screens from the Screens catalog, themes it, and exports it:

- **The studio** breaks out of the docs frame and uses the whole window: a 21rem panel of settings on the inline start, which folds away (its button, or ⌘\ / Ctrl+\; focus moves with it), and the live frame filling the rest. On phones the panel is the page and the preview is a step of its own.
- **Steps:** Frame, Parts, Screens and Theme (and, on phones, Preview). The panel's bottom edge holds the actions: the `npx @youj/cli create '<link>'` command with its copy, Shuffle, Start over, Copy link, and **Get the code**, which opens the export in the large code modal (a theme that misses AA swaps the command for a way to the issue). Settings are an inspector (`@youj/react/docs/inspector`): one row per setting, a menu for anything with named values (the frame parts show a wireframe per option, `schematic.tsx`), a switch for anything on or off, and fine-tuning folded under Advanced. Frame holds the layout, Parts the account, search and extras, Screens the picker (`screen-options.tsx`); Theme holds the component style, the size (`SizeControl`, `packages/ui/src/docs/create/size-control.tsx`: layout density and scale, compact at 90% by default, written on the export's root provider and in the link as `layout` and `scale`) and the Theming page's `ThemeBuilder`, controlled and `controlsOnly`.
- **Screens:** the picker offers every screen `taxonomy.json` tags `inApp` (one that lives in an app's content area: dashboards, tables, settings, billing, the assistant… not auth, checkout, marketing or status), which `packages/ui/scripts/generate.mjs` lists in `screens.generated.ts` (data, for the config and the CLI) and `screen-loaders.generated.tsx` (a lazy import each, for the preview alone). Grouped by category, with search; each added screen is a nav item, in its group (General, Workspace, Admin) and the order it was added there, which the arrows change; the first is home. None is valid: the frame alone. The preview's nav is the screens, a screen just added opens, and the export installs each screen's item, writes `lib/nav.ts`, a route per screen and `/` redirecting to the first.
- **Typefaces:** a curated catalogue of OFL families and 16 pairings (`packages/ui/src/docs/create/fonts.ts`). Nothing ships in the packages: the page and the preview load a family's Google Fonts stylesheet the first time it's shown (`load-fonts.ts`, or when a menu is about to open); an export sets up the ones its theme names with next/font (`packages/ui/src/docs/create/codegen.ts`), or a stylesheet `@import` without Next.js. A new family is one row in `FAMILIES`.
- **One source of truth:** the options, the parts they install, the URL format and the code generator live in `packages/ui/src/docs/create/` (`config.ts`, `theme-url.ts`, `look-url.ts`, `fonts.ts`, `codegen.ts`), shared with the stories and the CLI (`youj create <link>`). The preview renders the same plan the export prints (`render.tsx`), and `create.test.ts` typechecks the exported shell for every sidebar, top bar, account and search, every screen's route, the nav and the layout, every preset's theme and every pairing's next/font setup (against next's own font types). A new variant is a row in `config.ts` plus its block.
- **State is the URL:** the theme as its closest preset plus the fields that differ (a catalogue typeface by its key, `sans=geist`), the frame as the choices that differ from the default (the screens among them, `screens=analytics-overview,billing`; an older link's `page`/`pages` open as the closest screens), and the step; the page rewrites its own address as you go, so a frame is a link.
- **The theme's state** is a `Theme` (the motion contract), nothing Create-specific: `readTheme`/`writeTheme` (`theme-url.ts`) put it in a URL, `ThemeBuilder` edits it (`value` and `onChange`, or its own state from `initial`), `useThemeFonts(theme.fonts)` loads its typefaces, and `themeSource`/`fontsSource` (`codegen.ts`) write it out. Anything else that edits a theme (a site-wide Customise panel, say) can share it as is.
- **New theme fields** (a "character" token, say) need one row in `FIELDS` (`theme-url.ts`) to travel in the URL; their control belongs in `ThemeControls` (`theme-controls.tsx`), which the builder and Create show, and the export prints any field the theme sets.
- **Preview:** the showcase's `ViewportFrame` loading `/view/create`. The frame asks for the state over `postMessage` until the page answers (`lib/create.ts`), then gets each change live with no reload; light or dark, and the speed and reduced motion from the frame's Motion menu, come through `lib/frame-sync` (with `look={false}`, so the page's showcase look never reaches it). The theme and the link's component style apply inside the frame with `ThemeScope`.
- **Get the code** (`export-dialog.tsx`, on the site's shared `CodeExportDialog`) opens with the URL's `step=export` too, so old links still land on the code. It opens on **Command**: one line, `npx @youj/cli create '<link>'`, with a big Copy button and the theme's contrast check under it (a theme that misses AA blocks the command and the `.zip`, with a way to the issue), then the options (whether the frame's page comes along: off exports the frame alone) and the link to share. **Code** browses every file with the parts as installed (the showcase's `CodePanel`, read from `/r/<item>.json` when first needed), **Download** packs them into a `.zip` with a README (`lib/zip.ts`), and **Instructions** does it by hand: the `youj add` command, the shell and page files, then the theme (from the package or the copied source, or as plain CSS variables in `styles/theme.css`) and its fonts, each readable and copyable in place. The preview's Code tab still shows the same files.

## For machines

- **Markdown.** `lib/markdown.ts` renders any MDX page as Markdown: a preview becomes its example's code, `<InstallTabs>` the commands, `<PropsTable>` a props table, `<MotionSpec>` the token table, and visual-only embeds drop out. A test fails when a page uses a component it doesn't know, so give a new MDX component a case there.
- **Routes,** all prerendered: `/llms.txt` (the [llms.txt](https://llmstxt.org) index of the docs, blocks and examples), `/llms-full.txt` (every page), `/llms-small.txt` (each component's import, one line and main props) and `/docs/<slug>.md` (one page; `next.config.mjs` rewrites it to `app/llms.md`). `lib/llms.ts` builds them.
- **The MCP server** (`packages/mcp`) indexes the same Markdown, the registry, the props and the icon catalog. After changing docs, components or icons, run `pnpm -F @youj/mcp generate`; its `verify` fails while the index is stale.

## The hosted registry

`scripts/registry.ts` runs every workspace package's `scripts/build-registry.mjs` with `YOUJ_REGISTRY_URL=<site>/r`, copies each package's `public/r/*.json` into this app's `public/r`, and writes one combined `/r/registry.json`, named `youj` with the public site as its homepage, as the shadcn registry directory expects of `@youj` (`docs/launch/shadcn-checklist.md`). Item names share one namespace, so a name built by two packages fails the build.

### UI registry items

`packages/ui` ships its items the same way, through its own `scripts/build-registry.mjs`:

1. `registry/ui.json` is generated from the component sources by `scripts/generate.mjs` (`pnpm -F @youj/react generate`), along with the package entry.
2. Built items import each other and the motion files they use through the app's `@/` aliases, as shadcn's own items do, and their `registryDependencies` on motion items (for example `youj-core`) become full URLs under `YOUJ_REGISTRY_URL`.
3. It runs `shadcn build` into its `public/r`, which `scripts/registry.ts` copies here next to motion's items.

`<InstallTabs name="button" />` works for UI items, because it reads every `packages/*/registry/*.json` fragment.


## Package entries

Examples import the package entries (`@youj/core`, `@youj/motion`, `@youj/icons`, `@youj/loaders/<id>`, `/interactions`, `/backgrounds`, `/players`), the same imports an app writes. In the workspace they resolve to each package's `src/`; the published packages point them at `dist/`.
